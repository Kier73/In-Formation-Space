# PON-002 — signed, navigable orbit across public delivery providers

**Question:** Can an observer navigate a mathematical state described by immutable information that is retrieved through distinct, intermittently available public delivery services, without a permanently resident computational process, and without surrendering its own source-authorization decision?

PON-001 demonstrated exact CAG-001 arithmetic reconstruction from a temporary and a public static HTTP host, including after lease expiry. CAG-002 separately investigates live NATS/JetStream and libp2p message delivery. PON-002 advances a different frontier: *receiver-owned navigation policy, cryptographically checked source selection, dependency-directed retrieval, and cross-operator observations*.

## Network experiment and honest interpretation

Two independent GitHub-hosted jobs use **different publicly accessible HTTPS operators** to fetch the same five immutable CAG-001 packet descriptions from this repository:

- GitHub raw: an exact full-commit URL under raw.githubusercontent.com.
- jsDelivr: the same exact Git commit via cdn.jsdelivr.net/gh/Kier73/In-Formation-Space@COMMIT.

jsDelivr documents persistent CDN/S3-backed delivery of GitHub objects, but this experiment does **not** establish which internal storage location served any response, whether an S3 copy was created, whether cached content survives source downtime, or whether the origin can permanently disappear. Both providers share the same *GitHub repository source*. This is **operator-level delivery diversity**, not proven origin/storage independence or cryptographically independently administered provenance.

jsDelivr documentation: https://www.jsdelivr.com/documentation

IPFS could provide a different source/placement domain if someone deliberately pinned the exact objects; third-party gateways are retrieval services and must be independently verified against expected content identifiers, since gateways need not validate content for the consumer. No uncontrolled publishing or arbitrary public-gateway requests are performed in PON-002.

IPFS docs: https://docs.ipfs.tech/quickstart/retrieve/ and https://docs.ipfs.tech/quickstart/pin/

## Signed root capability

A receiver requires a *separately pinned* 32-byte Ed25519 issuer public key, the SHA-256 root manifest digest, a minimum accepted policy epoch, and a trusted time observation. A bounded issuer capability cryptographically binds:

- exact immutable root manifest SHA-256;
- issuer public-key SHA-256;
- policy epoch and short validity interval (maximum one hour);
- read-only / pure-CAG-001 computation purpose.

Unsigned grants, altered signatures, issuer-key substitution, a changed root, expired grants, future grants, and grants below the receiver's epoch floor all fail *before making any network request*. This is a test of the enforcement mechanics, not a claim that a public provider is itself an authority.

**Important authority limit:** the real HTTP experiment creates a short-lived signer separately in each GitHub job. Its public key travels in that job's evidence artifact, and its receiver pins that key for the operation. A third host can prove the public-key/signature relationship but cannot infer that the signing key belongs to an independent trusted issuer. The trusted-root input is rooted in the checked-in source and GitHub workflow. To establish external governance, a recipient must independently anchor the issuer key, its epoch floor, and its revocation policy using a mechanism such as COE-015–018 and RE-015. GitHub attestations on the main-branch run prove which *workflow* produced report bytes, not external source truth.

## What is navigated?

The manifest names immutable CAG-001 operation packets by semantic ID and SHA-256. Unlike PON-001's bulk manifest scan, PON-002 begins at the requested target and retrieves **only its dependency closure**. A manifest may list irrelevant operations without making the observer download them.

The canonical fixture is:

~~~text
final = (left + right) * 2
left  = seed + 4
right = seed * 5
seed  = 3

Verified value = 44
~~~

Each receiving observer:

1. verifies a signed, receiver-anchored root capability without contacting a provider;
2. checks the manifest's exact SHA-256 and canonical structure;
3. starts from the semantic target, recursively discovers predecessors and verifies every requested object against its content address and CAG-001 operation digest;
4. uses only restricted, immutable full-commit HTTPS URLs (or an explicitly allowed loopback fixture), disabling HTTP redirects, credentials, writes, arbitrary paths and oversized responses;
5. records each success, missing object and altered response as a separate route observation, with locally measured retrieval times;
6. can try another allowed route when a holder is unavailable, recording the failed route rather than suppressing that evidence;
7. computes the bounded exact pure result **locally** only after every necessary predecessor is recovered, conflict-free and mathematically reconstructable.

A simple failure-count preference changes the next route after an observed retrieval failure; it is not a claim of globally optimal scheduling. A missing predecessor stays unknown and no value is fabricated. An invalid object, including a malicious rewrite with a recomputed inner digest, cannot satisfy the receiver-pinned SHA-256 content address.

## How the live experiment verifies actual hosting

Workflow: .github/workflows/pon002-dual-public-providers.yml

- PR tests: source-capability, epoch, signature, path/redirect, corrupt/missing packet, causal closure, fallback and independent auditor unit tests across Python 3.11/3.13, plus PON-001 and CAG-001 regressions.
- Each public-provider job runs on a separate GitHub-hosted runner. It requests *every* required object only from its own public operator. A failure at that operator **fails that job**: fallback is not allowed to conceal a failed provider observation.
- A third runner downloads both report artifacts, verifies their independently produced short-lived grant signatures, checks each actual reported delivery operator and source revision, and independently recomputes exact result 44 from the checked-in canonical operation source.
- On the **main branch**, each producer additionally attests its exact report with GitHub Actions attestations, and the independent auditor verifies both artifacts' workflow signers and main-branch refs before reconstructing and attesting its own report.
- On a **pull request**, reports are not externally attested, so third-job comparison alone is weaker evidence than the main-branch attested run.

The provider reports include local wall-clock measurement samples, not synchronized multi-host duration or packet capture. They report actual HTTPS GET outcomes, not the physical cache tier, global path diversity, CDN survival guarantees or network-router computation.

## Precise claim boundaries

Demonstrated by the experiments only when CI has passed:

- immutable descriptions distributed on authorized public passive delivery services;
- receiver-anchored source-capability validity and mathematical identity checks;
- demand-driven navigation, unknown dependencies and alternative route selection;
- independent observer reconstruction of small exact pure arithmetic;
- separate run records from two delivery operators over real public HTTPS.

Not demonstrated:

- two independently administered object **origins**;
- source survival after GitHub disappears, deletion, or network partition;
- persistent third-party IPFS pins, programmable ISP router computation or autonomous CPU cycles in the transit wire;
- trusted issuance of the ephemeral research signing key;
- actual neural tensor/VM execution by a passive host;
- time-optimized geodesics, global transit-memory guarantees, or external effect authorization.

The structural model remains useful: a computation's verified *description* can be addressable independent of where its bytes are held, and time-dependent route availability changes which dependency paths can be navigated. The observer is where this bounded experiment actually realizes the arithmetic.

## After PON-002

A stronger PON-003 experiment should provision **two genuinely independent authorized storage origins** (for example, a deliberately provisioned IPFS pinning node and separately owned object bucket), with verifiable publication receipts, independently anchored signing keys, revocation epochs and failure injection that really takes one origin offline. A second frontier is integrating SNC-004's independently verified exact neural capsule as a typed orbit object, so transport and persistence can be passive while the receiving model host remains its own mathematical authority.

The transport, data-storage, mathematical-admission and effect-permission layers must remain independently testable.
