# IGC-002 — Receiver-owned execution of an intention-constructed Ground

**Status:** native E-CPU integration experiment built from IGC-001's proof-carrying regular-language Ground. No universal intention compiler, arbitrary code generation, physical-device attestation, mTLS or remote quorum claimed.

## Goal and reuse

An observer specifies an exact regular language of acceptable input sequences. IGC-001 constructs its minimal DFA without an imposed machine architecture. IGC-002 then admits and runs **one actual DFA step** through existing E-CPU HeadlessOS, SystemSeedEnvelope, VirtualGroundRef, OperatorRegistry, VirtualLayerWorkload, VirtualLayerRuntime, and Hypervisor authority. No new execution engine or source code is transported.

## Receiver sequence

1. Each receiver is provisioned with the original intention source path and a SHA-256 expected **outside** the candidate receipt. A standalone Node process independently validates all-word language equivalence (Thompson ε-NFA × proposed DFA), reachable-state prefixes, minimality certificates, source identity and capacity.
2. The receiver separately requires an **expected checkpoint SHA-256** from its local trust bootstrap. A stale input fails before execution even when internally consistent. The verifier replays all retained transitions from the constructed Ground, checks exact typed results, native effect contracts, event digests and sequence.
3. A completely new receiver process boots its own HeadlessOS and admitted native system Ground, binds an explicitly fixed pure DFA-transition handler, and configures its own processor capability.
4. Only a newly admitted E-CPU VirtualLayerWorkload can execute through the receiver's Hypervisor. A denied receiver never enters its handler. The resulting native virtual_layer.operator_result and journal are checked before one updated mathematical checkpoint is emitted.
5. The next receiver reconstructs the prior state without accessing the previous process, previous HeadlessOS instance, local capabilities or execution handler.

The fixture starts from the declaration (0|1)*01 and its independently proved minimal **three-state** machine. Four separate E-CPU receiver processes execute the symbols 0,1,0,1, yielding expected state sequence 1,2,1,2. Only the second and fourth words are accepted.

## Distinct proof and authority scopes

- The **mathematical Ground** is checked independently from the source intention. A two-state capacity request or contradictory language example cannot become runnable.
- Each actual new transition is checked by the **existing receiver-local Hypervisor**. Prior correct results, a source hash or a mathematical proof grant no future host authority.
- The receipt's earlier native effects are recomputed for structural/content consistency. Because historical receipts are not signed or protected by separate trust roots, this cannot authenticate who executed earlier work.
- The expected checkpoint digest is a caller-provisioned identity check, **not a persistent protected high-water or rollback-proof quorum certificate**. Real deployment must reuse existing E-CPU RecoveryLineage and authenticated authority.
- Receiver processes are independent OS processes on the same CI runner, with file-based handoff. There is **no authenticated mTLS link, network-routing proof, separate physical failure domain or remote cloud computation** in this experiment.
- The mathematical state is an observer-relative equivalence class of future distinguishable behavior, not an externally imposed hardware register architecture.

## Reproduce

The native verification workflow pins E-CPU commit 42aa58c289f62329deb14ced9b5d09f104b92837 and runs Ubuntu/Windows with Python 3.11/3.13, Node 22. Install the pinned checkout as an editable package, then run:

    python -m pip install -e external/E-CPU
    python -m unittest discover -s experiments/intention-ground-construction -p test_construct.py -v
    python -m unittest discover -s experiments/intention-ground-construction -p test_native_execution.py -v

The cases include separate process recovery; local privilege denial without handler invocation; stale expected checkpoint; self-rehashed false transition and operator effect; independently rejected forged source Ground; insufficient state budget and contradictory intention; source revision mismatch; unlisted token; invalid host ID; and an attempted receipt-defined authority grant.

## Next discriminating test

Reconstruct the existing workload as a real E-CPU HypervisorOperationChannel receive_and_execute message over mutual TLS, with a receiver-pinned operator and source, and fence the carried checkpoint through E-CPU's existing authenticated RecoveryLineage quorum. Independently kill the owner, rehome to another peer, and measure both transport bytes and source/verification/host work. Preserve exact failure semantics: stale lineages, correct-but-unauthorized execution, and self-rehashed fabricated Ground reports must refuse.

**Research interpretation:** IGC-001 proves that a particular mathematical machine must exist to realize the intended language. IGC-002 asks whether a newly bootstrapped observer-host can actually enact that verified behavior without inheriting unearned authority from another observer.
