# TCR-002 — Receiver-resident tensor cut over E-CPU authenticated channels

**Status:** experimental. A green local-socket CI run establishes process-separated loopback mTLS and application verification. It is **not** an independently hosted peer-to-peer overlay, nor yet a `TransitComputeWorker` / VirtualLayer/Hypervisor tensor operator. The live-model step is a separately fail-closed network test.

## Question

Can TCR-001's exact partition identities be admitted **by a receiver that owns the parameters**, with only typed activations and partial outputs traversing E-CPU's actual mutual-TLS `SocketTransport` / `ReliableChannel`, while the origin retains the original E-CPU DAG numerical verification?

## Design

The receiver is preprovisioned with one selected TCR-001 shard (`shard.npz`, `assignment.json`, `manifest.json`). Its `ResidentShard` validates every typed numerical digest, shape, dtype, local assignment and complete manifest **before opening a listener**. The origin only sends the immutable source/cut digest, partition ID, request ID, input digest and the bounded little-endian F64 activation bytes. It never sends `W1`, `b1` or `W2` in the warm request.

Each worker is a separate subprocess with its own ephemeral leaf certificate (`DNS:tcr002-worker-N`) issued by a process-local test CA. The origin certificate uses `DNS:tcr002-origin`. Both sides verify CA, DNS and the peer's client certificate via E-CPU's existing reciprocal TLS helper. Two independent `ReliableChannel`s transfer request and application response. Transport ACK means only delivery, not acceptance or mathematics. The receiving application enforces its own immutable cut policy and creates the typed partial receipt before the request ACK. The origin verifies response IDs, request hash, output bytes, receipt and TCR-001 partition identity before letting the existing E-CPU DAG aggregate. An independent dense reference plus scalar oracle still determines numerical acceptance.

Repeated identical request IDs are answered from a local process cache; a second reply has `replayed=true` and no recomputation. A manifest substitution must be denied **at the receiver** even if it arrives over authenticated TLS. The local runner explicitly exercises both cases. This is an in-memory replay cache, not a durable exactly-once guarantee across process restarts; future stateful tensor sessions should use E-CPU recovery-lineage authority instead.

## Reproduce

From the repository root on Linux with Python, NumPy, OpenSSL and the pinned E-CPU package importable:

```bash
python -m unittest experiments.tensor_cut_realization.test_transit_tensor -v
python -m experiments.tensor_cut_realization.tensor_cut prepare --out prepared
PYTHONPATH=external/E-CPU python -m experiments.tensor_cut_realization.run_transit_local \
  --prepared prepared --report tcr002-local.json
```

For a real GPT-2 MLP observation, run the existing `tensor_cut prepare --live` instead, with `jsonschema` available. CI pins E-CPU commit `3b57adcc2baaaa7e56e4bab943946f4e87e95c65` and produces separate local/procedural and live/pinned-parameter reports. Failed live acquisition never silently substitutes procedural coefficients.

## Evidence and cost interpretation

The report records client-local request-to-application-response intervals and receiver-local compute intervals independently. It records serialized request and response application byte counts over the two cycles, not full TLS/framing/IP bytes, model provisioning, system-wide wall time, or independent-host latency. Four worker processes on **one GitHub runner** share one operating system; this validates TLS sockets and separate receiver processes, not geographic distribution. The 18,889,728 selected source-parameter bytes are a **cold provisioning cost** and are excluded from the per-request activation count.

The application receipt inside the authenticated stream is digest-bound but not a portable digitally signed host attestation. The ephemeral CA is generated by the local experiment and is not a third-party device attestation. A compromised local trust bootstrap or source can still impersonate the system. The identity/policy acceptance is not delegated to E-CPU VirtualLayer/Hypervisor; it is a separately coded receiver-side numeric contract using E-CPU transport. None of these tests establish cross-host lease/fabric route authority, persistent recovery, universal functional equivalence, or speedups over a dense local accelerator.

## Next frontier

Use the same typed request and receiver-owned source policy with an actual E-CPU operator registered through the destination's VirtualLayer/Hypervisor and TransitBackendRouter, durable operation-id replay and content-addressed shard cache; then run the four receivers as independently hosted, authenticated overlay peers (with explicit Tailscale federation credentials and third-host reconstruction) and publish cold/warm transport, compute and provenance spans without inventing a shared clock.
