# TCR-001 — Tensor-Cut Realization

**Status:** experimental implementation, with real-parameter verification dependent on the live CI run. This is a bounded feed-forward MLP experiment, not general tensor inference.

## Question

Can one externally observed neural block be divided into *independent parameter-bearing execution loci*, with only input activations and output contributions crossing their per-operation interfaces, while E-CPU retains the dependency and result-commit structure?

For a standalone `affine -> elementwise activation -> affine` block,

\[
Y=\phi(XW_1+b_1)W_2+b_2
 = b_2+\sum_{k=0}^{p-1}\phi(XW_{1[:,I_k]}+b_{1[I_k]})W_{2[I_k,:]},
\]

where the `I_k` form a disjoint exhaustive partition of hidden-neuron indices. This identity holds over the reals for any shared **elementwise** activation. TCR-001 implements `relu` and GPT-2's `gelu_tanh`. It does not apply to attention or a coupling/normalization layer inserted *between* the two affine transforms. Floating-point reduction order can make decomposed outputs non-bitwise-equivalent.

## Existing foundations reused

- **In-Formation-Space HFR:** pinned public Safetensors manifest plus exact selected-range payload retrieval, not arbitrary code execution.
- **PNF-001:** `observed_block` validates the four actual GPT-2 layer-0 MLP parameter tensors against their graph, byte lengths, source revision, header identities, and selected-payload digests. The selected source block is `768 -> 3,072 -> 768`, with exactly **18,889,728** F32 bytes under the existing 20 MiB budget.
- **E-CPU:** real `ComputationNode` / `NavigableComputationDAG` nodes, readiness, result commits, digest-preserving snapshot reconstruction, and dependency ordering at aggregation. E-CPU's transport, route authority, and Transit workers are **not** used in this stage.
- **VGI:** its separate HFR topology obligations are not silently promoted to verified by numeric tests; no Lean/kernel proof is claimed.

## Actual multi-job protocol

A separate GitHub Actions **preparer job** obtains the source weights once. It emits four *individually provisioned* shard artifacts and a small reference artifact. Each separately scheduled **worker job** downloads only its own assigned shard (plus common activation input and its manifest). The **aggregator job** downloads worker output artifacts and the reference (but **not** the parameter shards), validates their typed identities, executes the E-CPU DAG, and checks all dense output coordinates against the reference and selected coordinates against a separately implemented `math.fsum` scalar oracle generated by the preparer.

```text
Source checkpoint + pinned HFR graph
           |
   bounded preparer job
           |
      4 disjoint weight shards + common X
         / | | \
     W0   W1 W2  W3         separate hosted worker jobs
      \    | |  /
      partial outputs
           |
    E-CPU DAG aggregator  <--- reference output + scalar oracle
           |
      checked result + immutable digest identities
```

**Honest network boundary:** GitHub Actions artifacts are *store-and-forward relay*, not a direct peer-authenticated E-CPU transport path. Runner jobs are separate scheduled execution environments, not independently attested physical machines. Receipts are unsigned. Worker outputs are verified against reference observations, but an attacker capable of replacing the whole preparer and its reference cannot be detected solely by these manifests. This does not establish a network-speed advantage or low-latency transport.

## Steps and evidence

1. Preparer checks exact supported source shapes and hashes, computes an immutable partition manifest, and writes one bounded packet per partition. One worker packet contains only its up-weight columns, up-bias slice, down-weight rows, and the common F64 input. The output bias is held by the aggregator, so it is applied **exactly once**.
2. Each worker verifies its manifest digest, explicit partition assignment, all shard tensor bytes and shapes, and the common input hash *before* execution. Each generates a typed F64 partial output and a receipt. An unsigned digest binds bytes to a declared identity, but is not peer authentication.
3. The aggregator recomputes all incoming partial digests, rejects missing or conflicting identities, commits four leaf nodes, adds contributions in declared partition order, applies the output bias once, and commits a `reduce` node.
4. A `verify` node compares every output to the independent dense NumPy evaluation (`rtol=1e-10`, `atol=1e-9`), and compares three selected output coordinates to the scalar `math.fsum` oracle. It persists the exact E-CPU DAG checkpoint and verifies restoration. A changed, even *rehashed*, worker partial must fail numeric reference comparison.
5. Reports contain tensor identities, source evidence, parameter partition ranges, operation receipts, numeric errors, logical data-volume estimates, and the E-CPU checkpoint. Raw model parameters and raw outputs are not included in the JSON report. **Worker artifacts do contain each worker's own source weight slice**, which is public MIT-licensed data.

### Cost accounting

The report's `logical_activation_and_partial_bytes` equals `partition_count * (input F64 bytes + partial-output F64 bytes)` for the declared probe count. For the 768-dimensional GPT-2 block, four workers, and two probes, this is **98,304 bytes**, before any metadata or transport framing. This **excludes** first-time provision of ~18.9 MB of parameter payloads and all GitHub artifact, HTTP, TLS, scheduling, verification, and recovery costs. It is not a measurement of bytes moved on a real E-CPU route, nor a speedup claim.

This deliberately tests whether an algorithmic representation has a plausible low-bandwidth *warm execution* interface. Cold model provisioning and the physical routing/latency of a future E-CPU Transit implementation must be measured separately.

## Reproduce

From the repository root with `numpy` installed:

```bash
python -m unittest experiments.tensor_cut_realization.test_tensor_cut -v
python -m experiments.tensor_cut_realization.tensor_cut prepare --out /tmp/tcr-prep
for i in 0 1 2 3; do
  python -m experiments.tensor_cut_realization.tensor_cut worker \
    --packet /tmp/tcr-prep/shard-$i --out /tmp/tcr-results
done
```

With an E-CPU checkout on `PYTHONPATH`, complete the DAG-backed check:

```bash
python -m experiments.tensor_cut_realization.tensor_cut aggregate \
  --prepared /tmp/tcr-prep --results /tmp/tcr-results --out /tmp/tcr-report.json
```

For the pinned real model, add `--live` to `prepare` with `jsonschema` installed and the existing HFR/PNF modules. The dedicated [TCR-001 workflow](../../.github/workflows/tensor-cut-realization.yml) performs live preparation on one hosted job, four separate worker jobs and aggregation on another, after offline tests pass. A network failure fails the live preparation; it is never replaced with synthetic weights under a `live` label.

## Verification categories

| Category | Established by this experiment? |
| --- | --- |
| Real source tensor binding | Yes only if pinned live HFR preparation completes |
| Exact algebraic decomposition | Derivable for the stated real-arithmetic/elementwise-activation contract; not machine-checked |
| Numeric equivalence | Only the declared finite probes and tolerance, not all inputs or bitwise FP32 |
| Independent scalar cross-check | Three selected output coordinates on the same two probes |
| Separate hosted worker executions | Yes if the multi-job workflow completes |
| E-CPU dependency scheduling, commits and restore | Yes if aggregator job completes |
| E-CPU peer-to-peer execution over authenticated Transit | **Not yet** |
| Verified publisher signature, remote hardware attestation | **Not established** |
| General transformer inference or performance improvement | **Not established** |
